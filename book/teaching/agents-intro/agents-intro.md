## Who this is for, and how to read it

models, and have heard the word "agent" often enough to be tired of it. The lecture builds
from concept: context, then mechanism, then the four ways to use one, then the pieces that
let a model act (the model, the tools, the permissions, MCP), then where it pays off, then

**Speaker notes**

Four words on one slide, large, and the whole lecture is detail on them. The *LLM*
predicts the next token and never executes anything. *Tools* are its hands: the shell, so
scripts, Python, git and whatever software the environment has; files; the web. The
*harness* is the program around the model that reads a *tool call*, the model writing
"run this function with these arguments" in a fixed format, checks whether it is allowed,
runs it, and hands the result back. The *loop* is the harness doing that until the model
stops asking. Leave the slide up until the room can say the sentence at the bottom back:
an agent is a model, with tools, in a harness, in a loop.

Start from what everyone in the room has already used. A chat box appeared in front of a
language model on 30 November 2022, on a model called GPT-3.5 [@wikipedia2026chatgpt].
Text in, text out, and the model could not touch anything. Within months the same page
records plugins, in March 2023, alongside GPT-4: the model could now ask for a function to
be called. That is the conceptual step from a chatbot to an agent, and the rest has been
training and engineering around it: models trained after their main training, which is
what "post-trained" means, to plan, call tools, read the results and debug, which the
eScience workshop description names as the thing to understand about these systems
[@escience2026codingagents].

Three dated stages follow. In November 2024 a standard for plugging tools in was
announced, the Model Context Protocol, which its own site defines as an open-source
standard for connecting AI applications to external systems [@anthropic2024mcp; @mcp2026site].
In February 2025 the vendor whose tools this lecture uses released what it called its
first agentic coding tool, as a limited research preview: a program that searches and
reads code, edits files, writes and runs tests, and commits [@anthropic2025claudecode].
Other vendors had coding agents before that date; this is one vendor's timeline, not the
field's, and dating the others from fetched sources is a TODO. And the window grew: GPT-3
held 2,048 tokens [@wikipedia2026gpt3]; the largest current models on the vendor's page
hold one million, which that page converts to roughly 555 thousand words, and the smallest
holds 200 thousand [@anthropic2026models]. A million tokens is enough for a repository, its
documentation and a day's transcript at once.

Then the point of the slide, which is the lecturer's reading and says so. The window was a
big step, but what made this usable is the infrastructure around the model. Fewer
hallucinations: retrieval is now a tool call whose result, real papers, re-enters the
window, and the model grounds claims in them rather than inventing them; the June post
puts literature review close to solved for a working scientist on that basis
[@denolle2026three]. Tool results are facts the model has to read: when it runs your test
and the test fails, the failure is in its window. And the files around the model: the
standing instructions that say what you want, and the tests that say what done means, are
what turn a model into something you can hand a task to. The harness runs against your
repository, so the unit of work is a pull request rather than a pasted snippet.

Two more sentences for the room. It moves fast: new model types are being built for
decisions, text in and a probability out, and the harness does not care which model sits
under it. TODO: the lecturer's example, given as "JEV", to be named and cited from a
fetched page before it is said. And geoscience is lagging, which is why this lecture
exists. Hold the sceptic's question, "why an agent rather than a script", until the
payoff segment, where the answer is the spec.

## What an agent is, mechanically

**Slides**

6. One table: open-weight model, private model, prompt, agent.
7. Chat, script, agent ([](#fig-agent-loop)).
8. The whole thing as code: ten lines, one tool call as JSON, what the harness is.

```{figure} ../../img/agent-loop.svg
:name: fig-agent-loop
:width: 100%

Three ways to put a language model to work. In a chat session (A) the human closes every
loop. In a fixed workflow script (B) every branch was written in advance. In an agent loop
(C) the model reads the result of its last action and decides the next one. The human always
enters at the start, with the goal, the rules and the stop condition; where else the human
enters is the design question.
```

**Speaker notes**

Three definitions first. A *model* is a function from a token sequence to a probability
distribution over the next token. An *open-weight* model is one whose parameters you can
download and run on your own hardware; HazEvalHub's prototype ran a 7 billion parameter
Qwen and an 8 billion parameter Llama locally next to cloud models
([HazEvalHub](../../chapters/hazevalhub.md)). A *private* model is reached only through a
vendor's API: you never see the weights, you pay per token, and the vendor can change the
model under you. "Writing a prompt" places text in the model's window and asks for a
continuation. Nothing else happens; a chat interface hides that by re-sending the
transcript on every turn.

Then the figure. Panel A is chat: you close every loop, and quality is bounded by your
patience for closing loops. Panel B is the workflow script everyone here already writes:
deterministic, every branch written in advance, and an unexpected input is a crash that a
person reads about in a log. Panel C is the loop. The model is given a goal and tools; it
gathers context, acts, verifies, repeats. The difference from A is that the model closes
the loop. The difference from B is that the model chooses the next step from what it just
observed, so an unexpected state becomes a decision, which can be wrong or endless; a crash
at least stops. Now the human. You are always in the loop at the start: the goal, the
rules, the stop condition. Where else you sit is the hardest design question, and it has
four real answers in this lecture: on every action, as the permission prompt; on every
diff, as the app shows them; only at the end, as a pull request review; or nowhere, as a
headless run. The trend is toward less, and the guardrails segment is about what has to
replace you when you leave. The four verbs are our labels for what the tool calls turn out
to be. The model has no stages, only one token stream.

*The whole thing, mechanically.* This is the slide the room needs. The model is called once
per turn with the whole message list and returns tokens. If the returned tokens end in a
structured tool-call block, the program around the model, the *harness*, parses it, checks
permissions, runs the function, appends the result as a new message, and calls the model
again. Nothing else happens: no memory, no execution inside the model, no stages.

```python
messages = [system_prompt, context_file, tool_schemas, task]
while True:
    out = model(messages)                      # one API call: tokens in, tokens out
    if out.stop_reason != "tool_use":
        break                                  # plain text: the model says it is done
    if not permitted(out.tool, out.args):      # the harness pauses here, not the model
        result = "denied by user"
    else:
        result = run(out.tool, out.args)       # shell, file, web, GitHub ...
    messages += [out, tool_result(result)]     # the result re-enters the window
```

The four names on the first line: the system prompt is the harness's own standing text;
the context file is the standing instructions in your repository (the pieces segment); the tool
schemas are the list of functions the model may call, each with a name, a description and
an argument schema; the task is what you typed. A tool call is structured tokens, for
example `{"name": "bash", "input": {"command": "pixi run spellcheck"}}`; the model was
post-trained to emit that format and the harness only parses it. One turn can carry
several tool calls; the sketch shows one for brevity. Why a tool at all:
next-token prediction cannot execute, count, or do arithmetic reliably, and a shell with
Python in it is the workaround. A subagent is this same loop started again with a fresh
message list, launched by a tool call, whose final text comes back as a tool result. A
permission prompt is the harness pausing between parse and run; a denial is just a string
the model reads next. The pieces segment introduces the named pieces; say then which are one vendor's
conventions and which are general, because someone will ask whether this is a Claude
course. It is not; the loop is the same everywhere.

The loop is only as good as its *verify* step: an agent that cannot run the tests, or is
not told to, will report success on the strength of having edited a file. And the loop has
no natural end. It stops when the model says it is done, when a budget runs out, or when a
person kills it. We will see all three today.

```{figure} ../../img/agents-four-ways.svg
Four ways to use a coding agent today. The browser's Chat tab has no path to your
```

**Speaker notes**

The vendor documentation lists the surfaces: the terminal, IDE extensions for VS Code and
JetBrains, a desktop app, and the web, all connecting to the same engine so a repository's
context file, settings and MCP servers work across all of them [@claudecode2026overview].
Note the vendor's "web" surface is the agent running in the cloud on a repository, at
the site's Code tab; the site's Chat tab is not, and that distinction is the whole of the
first row below. For this room the useful cut is: what can it touch, who is watching,
what does it need, and does it run on the cluster.

*Browser chat.* The Chat tab at the vendor's site. It cannot see your files or run your
code. It is the right tool for questions, drafts and reading papers, and the wrong tool for
anything that ends in a commit. Most people in the room have used only this, and most of
what they believe about "AI coding" comes from pasting snippets into it.

*The app.* The desktop app has a Chat tab and a Code tab. The Code tab is the agent: it runs
against a directory on your machine and shows each diff visually before it lands, and the
documentation notes it can run several sessions side by side and schedule recurring tasks.
The point to make is that Chat and Code are the same model with and without the loop and
the tools; switching tabs is switching from panel A to panel C of the figure.

*The editor.* The VS Code and JetBrains extensions put the same agent inside the editor,
with inline diffs and plan review. This is the mode for changes you want to read line by
line as they happen. TODO: one screenshot from a real session on this repository.

*The CLI.* The terminal is the full-featured surface, and the only one of the four that
is a plain terminal program, so it runs over ssh on a cluster login node provided that
node can reach the model API; whether a compute node can is the site's network policy,
and a TODO for each cluster the room uses. Editor extensions with a remote-editor setup
may also work; that is a TODO, not a no. Interactive
`claude` for exploration and anything you want to watch, with each gated action, meaning
a tool call the permission settings say must be approved, asking before it runs;
`claude -p` for the non-interactive mode, which takes a prompt, runs the loop without a
terminal, and exits, so it can be piped, scripted, and run in CI
[@claudecode2026overview]. That is the mode for a queue of work, and it takes three parts. First the
issues: one task each, scoped, with a done condition, and a label the loop can select on;
the issue is the specification, so the discipline of the payoff segment applies to it.
Second the loop, on any machine with a shell, the repository and a key:

```bash
for n in $(gh issue list --label agent --json number --jq '.[].number'); do
  claude -p "Make the smallest change that resolves issue #$n; run the tests; open a PR." \
    --max-turns 40 --max-budget-usd 5 --output-format json \
    --permission-mode acceptEdits --disallowedTools "Bash(git push --force *)" \
    > "runs/issue-$n.json"
done
```

The flags are the vendor's [@claudecode2026cli]: `--max-turns` and `--max-budget-usd`
bound the run, `--output-format json` keeps a record of it, and the permission mode and
deny rules decide what it may do unattended; the reference documents no wall-clock flag,
so the scheduler or a `timeout` wrapper supplies that. Third, the human at the end: every
run ends in a pull request that a person reads, merges or closes. Two ways it goes wrong,
to say aloud: a run that never satisfies its own done condition spends its budget and
stops, which is the point of the budget; and a run with edit permissions and no deny rules
can push, which is the point of the deny rules. The group has run this pattern; the
lecture keeps the pattern and not the machine, the issues or the logs, which are internal.

Other vendors ship the same shapes. The lecturer's own comparison names one, OpenAI's
Codex, as the app-and-CLI equivalent; a table of equivalents with fetched links is a
TODO. The names differ, the loop does not. Where a first-timer should start: the app's
Code tab, because it shows every diff before it lands; the tutorials use the CLI because
its transcript can be captured.

**Speaker notes**

*The overview, four things.* One: the LLM predicts the next token and was trained to emit
a tool call as structured text; it never executes anything. Two: the tools, which for a
computational scientist are the shell (scripts, Python, the scientific software already
installed in the environment, git), the file tools (read, edit) and the web tools (fetch,
search). Anything you can run at a prompt the agent can run through the shell tool, which
is why "can it run ObsPy" has the same answer as "can you". Three: the permissions, the
harness's gate between the parsed tool call and its execution. The vendor's page states
the defaults: read-only tools such as file reads and searches run without asking inside
the working directory; shell commands ask, except a built-in set of read-only ones; file
edits ask; web fetch and search ask [@claudecode2026permissions]. On top of the defaults
sit allow, deny and ask rules, written per tool and pattern, for example allow
`Bash(git commit *)` and deny `Bash(git push *)`, and modes that shift the whole gate:
`plan` reads and runs read-only commands but edits nothing, `default` asks on first use
of each tool, `acceptEdits` stops asking for edits, `auto` lets a classifier approve, and
`bypassPermissions` skips prompts and is meant for containers. One sentence from that
page is the one to read aloud: permission rules are enforced by the harness, not by the
model; instructions in a prompt or a context file shape what the model tries, they do not
change what is allowed. Four: MCP, the open standard for tools that live outside the
harness, which the vendor's page describes as giving the agent access to your tools,
databases and APIs [@claudecode2026mcp; @mcp2026site]. An MCP server advertises its tools
with the same name, description and schema as a native tool, so to the model a data
catalogue looks like one more function. That is what lets a model plus tools act on the
world beyond the repository, and also what adds a party whose output the model will act
on.

*The context file.* The coding agents this lecture uses look for a standing instruction
file in the repository root; other products keep theirs elsewhere. Claude Code reads
`CLAUDE.md`, and the vendor documentation says it can also read an `AGENTS.md` written
for other coding agents [@claudecode2026overview]. Ours is worth showing for what it is
not. `CLAUDE.md` is five lines that point at `AGENTS.md`. `AGENTS.md` fits on one screen:
what the repo is, the layout, the build commands, seven conventions, and one paragraph
about persona reviews. It does not explain MyST, does not restate the contributing guide,
and does not tell the agent how to write Markdown. The March post frames this as three
layers: a knowledge anchor, standing instructions, and the situated prompt; the first two
determine output quality, and the instructions are a living document
[@denolle2026beforeprompt].

*Where the files live.* Everything on the overview slide is a file in the repository, and
the room should know where. From the vendor's pages and this repository:

```
your-repo/
├── AGENTS.md, CLAUDE.md        standing instructions, read at the start of every session
├── .claude/
│   ├── settings.json           permissions: allow / deny / ask rules, shared with the team
│   ├── settings.local.json     your own rules and approvals, git-ignored
│   ├── skills/<name>/SKILL.md  procedures loaded on demand (writing your own)
│   └── agents/<name>.md        subagent definitions: role, tools, model, permission mode
├── .mcp.json                   MCP servers for this project, shared via git
├── review-logs/<date>/         what the agents wrote, dated
└── src/  tests/  docs/  SPEC.md
```

The settings paths and their scopes are the vendor's [@claudecode2026permissions], the
MCP file and its three scopes likewise [@claudecode2026mcp], and the agents directory is
where the subagent page says definitions live, with a per-user copy under the home
directory [@claudecode2026subagents]. This repository ignores everything under `.claude/`
except `skills/`, `agents/` and the persona definitions, so local approvals never reach
git. Say that once; it is the answer to "what did you commit".

*The context window.* The window is finite. It holds, in order, the system prompt, the
context file, the tool and skill descriptions, and then the running transcript. Tool
results are the part people forget: one `cat` of a large log can consume more of the
window than the whole conversation so far. When the window fills, the harness used here
compacts, and compaction is itself a model call: the harness asks the model to summarise
the older messages, then swaps them for the summary, so the loss is sampled text, not a
deterministic truncation. A rule stated in the first prompt may not survive; a file read
at minute two may have to be read again. And in retrieval experiments, recall drops for
material in the middle of a long context relative to either end [@liu2024lost]; the
analogous risk for an agent is that forty files "read" into the window were sampled, not
read. In practice: invariant rules go in the context file, not the prompt; big reads go
to a subagent; a new task gets a new session; and when a well-behaved agent starts to
drift, suspect the window before the model.


*Skills, and MCP again.* When would you write a skill rather than a paragraph in
`AGENTS.md`? When the procedure is long, is needed only sometimes, and would cost every
session if it lived in the context file. A skill is a folder with a `SKILL.md` and any
reference files it needs. The harness puts every description into the window at startup;
the *model* decides to use a skill, and only then does the harness load the body. So a
skill costs its description on every call, whether or not it fires, and its body only
when loaded. That is why the description is the part to keep short, and why "fix the
description" is the remedy when a skill does not trigger. This repository ships one,
`plain-voice`, which strips language-model vocabulary out of prose; its description is
about 60 words, its body about 2300. We build a second one live in the writing-your-own segment.
Which of these are one vendor's and which are general: `CLAUDE.md`, skills and the
`claude -p` flag are the vendor's conventions; `AGENTS.md` is the cross-vendor file its
documentation says it also reads [@claudecode2026overview]; MCP is a published standard.

```{figure} ../../img/agents-payoff.svg
:name: fig-agents-payoff
:width: 100%

Where an agent pays off in a computational-science workflow. You write the spec and you
```

**Speaker notes**

This is the answer to "why an agent rather than a script". A script is the right tool when
you already know every step. An agent is the right tool when you can state what done looks
like but not yet how to get there, and when getting there is mostly typing you have done
before. Five uses, from this group's practice, in the order they happen in a project.

*Write the code specification.* Before any code: what the program takes, what it produces,
which conventions it follows, what a passing test looks like, and what is out of scope. Ask
the agent to draft the spec from a conversation and then edit it yourself; the spec is the
contract and everything after is checked against it. A one-page skeleton is enough:

```
# SPEC: <name>
1. Purpose: one sentence.
2. Inputs: files, formats, units, coordinate frames.
3. Outputs: files, formats, units; what a plot of them should look like.
4. Conventions: package layout, style, test runner (pytest), CI (GitHub Actions),
   licence (MIT), the checks that must stay green.
5. Done when: pytest tests/test_<name>.py passes; docs/figures/<name>.png shows <what>.
6. Out of scope: what not to touch.
```

The numbered sections are what the prompts below point at, and naming the runner, the
CI and the licence in section 4 is what stops the agent choosing them for you. The June post's phrase for the
division of labour is that the scarce resource is the human bandwidth to check the work;
the spec is what makes checking possible [@denolle2026three].

*Intent- and goal-oriented coding.* "Implement section 3 of `SPEC.md`; stop when
`pytest tests/test_io.py` passes" rather than "write a function that opens the file". You
state the goal and the stop condition; the agent picks the steps. If the test named in the
stop condition does not exist yet, ask for it first from the spec, which is use 4 below;
on a new module the tests come before the implementation even though the list numbers
them the other way. This is the mode the
figure's panel C describes, and it is where the loop earns its cost.

*A repository template.* "Set up a Python repository for X using pixi and best current
standards": a `pyproject`, a test directory with one passing test, continuous integration
that runs it, a README that says how to install and run, a licence, a `.gitignore`. Check
the result against that list. In the lecturer's experience this is an afternoon of
boilerplate that the agent does in minutes; the coordination plan's `gaia-template-agent`
(the GAIA segment) is this use made reusable.

*All the CI tests for X.* "Write the tests for module X from section 5 of `SPEC.md` and
run them with pytest. If a test fails, tell me whether the test or X is wrong before
changing either." That last sentence replaces "do not change X to make a test pass",
which the agent resolves by declaring the test right whenever fixing X is easier; asking
for the judgement first puts it in the transcript where you can check it. The tests are
the verify step for every later change. The vendor's own
documentation lists writing tests for untested code as the first thing to hand over
[@claudecode2026overview]; whether it pays off is for the tutorials to measure.

*Make sure you can see the raw data.* "After each function in `pipeline.py` that returns
an array, save a figure of its output to `docs/figures/<function>.png`, and for each
table save its first and last five rows to `docs/figures/<function>.txt`; list them all in
the README." Name the functions or the file, not "every stage", or the agent decides what
a stage is. This is how you check an agent's
work without reading every line it wrote, and it catches what tests miss: tests written by
the same agent inherit the agent's reading of the spec, and the raw data do not. If the
raw data look wrong, the pipeline is wrong, whatever the tests say. It is the one use on this list that is specific to science, and the one the room
should leave with.

*The live demo.* Before the talk, add a scratch page `book/teaching/demo.md` with one
misspelling that codespell's dictionary knows (receive with the i and e swapped is one), confirm with
`pixi run codespell book/teaching/demo.md` that it is reported, and do not commit the
page. Scope the task to that file, because the repository-wide `pixi run spellcheck`
would also report any other uncommitted typo in the working tree and confound the lesson.
Open the agent in this repository and say: `codespell book/teaching/demo.md` reports an
error; fix it and show me that command passes. The audience watches the check run, the
page get read, one word get edited, the check rerun and exit 0. Two minutes. The task was chosen because it has a real act and a real verify,
and because the pass condition is the repository's own check rather than the model's
opinion. If the agent edits more than one word, that is the minimal-change rule in `AGENTS.md`
being broken in front of the room; say so. Delete the scratch page afterwards.

**Speaker notes**

Three ways, in increasing order of how much you own, and a rule for choosing. First,
the zero-th option: a rule that is short and always applies belongs in `AGENTS.md`. A
skill when the current session should follow a longer procedure in its own window. An
agent definition when the task needs a fresh window, a narrower tool list, or parallel
copies. A loop in Python when you need a tool the harness does not have, a run you control
end to end, or a model the harness does not drive; tutorial 4's locally served model is
the last case, and the vendor SDK's client takes a `base_url` for a server that speaks the
same API (TODO: verify with the server eScience chooses).

*A skill.* A folder with a `SKILL.md`: a name and a description in the front matter, the
instructions below. Build one live. The problem: the governance page
[How we work](../../governance/how-we-work.md) carries the acknowledgement wording for the
three linked NSF awards and requires it verbatim; an agent asked to "add the
acknowledgement" will paraphrase. The skill, verbatim; the file is `.claude/skills/nsf-acknowledgement/SKILL.md` and its
first line is the front-matter fence:

```
---
name: nsf-acknowledgement
description: Insert the agreed GAIA acknowledgement wording for the NSF
  awards, verbatim, when a page, talk, poster or paper needs a funding
  statement.
---
1. Read the block-quoted wording from book/governance/how-we-work.md, section
   "Acknowledgement". Never embed it here.
2. Insert it verbatim, all three award numbers included, under an
   "Acknowledgements" heading at the end of the page unless told where.
3. If the seed grant or the Paros Center contributed, append the clause that
   page gives below the block quote, in place of the final full stop.
```

Type it, save it, then ask in a fresh
session for "a funding acknowledgement on `mt-rainier.md`" and watch whether it triggers.
If it does not, the description did not match; fix it in front of the room. That failure is
the more instructive outcome. There is a tradeoff to name: a longer description with more
trigger phrases fires more reliably, because the model is the matcher, and costs more per
call. What a skill is not: loading it is itself a tool call, but it adds no capability, since
it can only use tools the agent already has; and it is not a subagent, it runs in the
parent's window. It is a procedure written once by someone who knew the
rule.

*An agent definition, which is what a subagent is.* The vendor's page defines subagents
as specialised assistants for specific kinds of task, to use when a side task would flood
the main conversation with search results, logs or file contents, and states that each
runs in its own context window with its own system prompt, tool access and permissions
[@claudecode2026subagents]. Mechanically it is the loop from the mechanism segment started
again with a fresh message list, launched by a tool call, whose final text comes back to
the parent as a tool result. The definition is a Markdown file under `.claude/agents/`,
with front matter the page lists: `name`, `description` (when to delegate to it),
`tools`, `model`, `permissionMode`, `maxTurns`. An illustrative one:

```
---
name: review-hydrologist
description: Read one book page as a hydrologist would and report what a
  hydrologist would question, in the shared report format.
tools: Read, Grep, Glob, WebFetch
model: sonnet
permissionMode: plan
maxTurns: 30
---
Read shared/method.md, then shared/rubric.md, then the page. Report only in
the format rubric.md gives. Cite the line you are questioning.
```

*Its rubric and references.* The instructions are two lines because everything that
makes the reviewer consistent lives in files it reads at run time, not in the prompt: a
*method* file (what to open, in what order, a timebox, whether it may read other reviews)
and a *rubric* file (the dimensions to score, a severity scale, evidence rules, and the
exact report format). Those two files are shared by every reviewer, so ten of them judge
against one standard, and the output is one dated file per reviewer under `review-logs/`.
That is the whole trick of a specialised agent: references and rubric are files, the role
is a paragraph, and the harness supplies the loop.

```{figure} ../../img/agents-anatomy.svg
:name: fig-agents-anatomy
:width: 100%

One specialised agent: the definition file, the shared method and rubric it reads at run
time, the timeboxed loop, and the one file it writes. The reader role is illustrative.
```

*Adversarial reviews.* Once a reviewer is a file, ten reviewers are ten files, and an
orchestrator can run them in parallel on the same page, each in its own window, none
seeing another's output, and then synthesise: keep what three or more raised, keep
disagreements as disagreements, list the blockers, and report scores as a table rather
than an average. Isolation stops reviewers copying each other; it does not remove the
weights they share, so convergence between them is a lead to check, not a statistic. And
ten reviews cost ten windows' worth of tokens, not fewer; what they buy is a fresh window
and undivided attention per reader. The readers in the figure are illustrative roles;
choose them for the page under review. Prompt injection enters here too: a subagent's
report re-enters the parent as a tool result, and tool results and instructions are one
token stream with no provenance bit, so the merge step should keep only the fields the
report format defines. Tutorial 3 does exactly this with two readers.

```{figure} ../../img/agents-orchestrator-vs-specialist.svg
:name: fig-agents-orchestrator
:width: 100%

Adversarial reviews: ten readers in parallel and in isolation against one shared rubric;
a synthesis step merges the ten reports. The roles are illustrative.
```

*A loop in Python.* The vendor SDK exposes the loop directly. With the Python SDK, a tool
is a decorated function and the runner drives the loop; eighteen lines is a working agent
with one tool, as documented in the SDK's own reference, from which the shape below is
taken. To run it: `pip install anthropic` (it is not in this repository's pixi
environment), Python 3.10 or later, a key in `ANTHROPIC_API_KEY` or the vendor's login,
and `codespell` on the path, which the pixi environment provides, so run it with
`pixi run python`. `codespell` is the dictionary-based spellchecker behind
`pixi run spellcheck`. The tool only checks, so the task is to report, not to fix; an
edit tool is the next thing you would add, and the `client.beta` prefix says the runner
is a beta helper.

```python
import subprocess
import anthropic
from anthropic import beta_tool

client = anthropic.Anthropic()

@beta_tool
def spellcheck(path: str) -> str:
    """Run the repository spellcheck on one file and return its output."""
    r = subprocess.run(["codespell", path], capture_output=True, text=True)
    return r.stdout or "clean"

task = "Run the spellcheck on book/teaching/demo.md and report."
runner = client.beta.messages.tool_runner(
    model="claude-opus-5", max_tokens=16000, tools=[spellcheck],
    messages=[{"role": "user", "content": task}],
)
for message in runner:   # one iteration per model turn; stops when no tool is called
    print(message)
```

The same reference documents the manual loop underneath: call `messages.create`, check
`stop_reason`, run each `tool_use` block, append a `tool_result` carrying the block's id,
repeat. That is the code slide from the mechanism segment with real names. For a batteries-included
harness as a library, with file tools, subagents and permissions, the vendor documentation
points at its Agent SDK [@claudecode2026overview]; other vendors have equivalents. TODO:
verify the runner example against the installed SDK version before it is shown, and add
the Agent SDK link from a fetched page.

**Speaker notes**

*Guardrails.* Three are in the coordination plan (section 6): a human approves anything
outward-facing, agents draft it; no fabricated DOIs or citations, provenance must be real;
secrets stay in GitHub Secrets and never in a repository. Two more come from practice: the
minimal-change rule, and bounded runs. The June post adds a structural one: agents that
critique other agents, with the critique on the record [@denolle2026three].

*Trajectory capture.* A trajectory is the full sequence of prompts, outputs, tool calls and
results for one run. We need it to audit, to score process and not only outcome, and to
reproduce. Four candidate mechanisms, none verified for our setup: the harness's own session
log; structured JSON output from headless runs; an evaluation harness that wraps the agent,
which is what the FrugalMind prototype does; a logging proxy in front of the model API. The
decision belongs to the group: which default, where stored, who may read.

*Why two runs differ.* Tutorial 4 scores reproducibility as the fraction of identical
outputs across N runs. The next token is sampled, not taken as the argmax; the vendor API
used here exposes no seed, and on its newest models accepts no sampling parameters at all,
so you cannot even ask for the argmax (older models on the same page still take a
temperature). Batched inference on shared accelerators is
generally not bit-reproducible (TODO: cite a source for this before it is said aloud). A model name can point at new weights; the vendor's page says its current model IDs are
pinned snapshots, so record the ID with every run. And the world moves: the page, the
dataset, the repository the agent touched differ between runs, and only the trajectory
records what it saw. Reproducibility of an agent run
is statistical: report N, pin versions, keep every tool result.

*Cost.* One of the three June experiments, one person using the coding agent on one
project, ran at about 200 dollars a month in API charges as the post states it, with no
model or run count given [@denolle2026three]. For scale, the vendor's page prices its
current models between 1 and 10 dollars per million input tokens and 5 to 50 per million
output tokens [@anthropic2026models]. HazEvalHub's prototype scores every submission on three questions and
plots cost against performance ([HazEvalHub](../../chapters/hazevalhub.md)); its early
result, as the page states it, is that free local 7 to 8 billion parameter models reach
perfect scores on configuration tasks once given domain skills and fail numerical code
generation, where only cloud models succeed, at about 0.56 without skills and 0.76 with.
Task counts and the number of runs behind those figures are not on the page and are a
TODO. Cost is a first-class axis for every agent we ship, recorded per run and reported
next to accuracy.

*Reproducibility.* The June post argues that if an agent cannot reproduce your work, neither
can your collaborators, and proposes a Reproducibility Statement in every paper beside the
data availability statement [@denolle2026three]. The coordination plan already requires a
provenance YAML and an RO-Crate per agent and publication. The missing link is the
trajectory inside the provenance record, which is what
[tutorial 4](tutorials/04-evaluating-agent-runs.md) builds toward.

*The tutorials.* Four stubs under Teaching, code cells to be filled with eScience: anatomy
of an agent, your first skill, subagents and orchestration, evaluating runs. Ask who joins
the dry run. The sources slide follows for the recording and is not narrated.
