## Who this is for, and how to read it

The audience is the GAIA team: people who are fluent in scientific computing, have trained
models, and have heard the word "agent" often enough to be tired of it. The lecture builds
from concept, gives the context before the mechanism, and says plainly which words are one
vendor's and which are general. The examples come from this repository, from the blog
*Agents for Academic Practice* [@denolle2026blog], from the UW eScience workshop
*Coding with AI Agents* [@escience2026codingagents], and from vendor documentation fetched
on the date given in each citation. Where a story has been told in the group but not
written down, the slot is a TODO.

Each section below is one segment. The heading carries the minute range. Under it,
*Slides* lists the slides to make, *Speaker notes* is what to say, and *Timing* flags where
the plan is tight. The diagrams are generated by `slides/figscripts/make_diagrams.py` into
`book/img/` and are shared with the deck.

**Speaker notes**

Start from what everyone in the room has already used. A chat box appeared in front of a
language model in November 2022; the page for it records the release date as 30 November
2022 and the first model as GPT-3.5 [@wikipedia2026chatgpt]. Text in, text out, and the
model could not touch anything. Within months the same page records plugins, in March
2023, alongside GPT-4: the model could now ask for a function to be called. That is the
whole conceptual step from a chatbot to an agent, and everything since has been
engineering around it.

Three stages followed, and I give them in order rather than by date because I have not
verified the dates. Models were post-trained to plan, call tools, read the results and
debug, which is what the eScience workshop description names as the thing to understand
about how these systems work [@escience2026codingagents]. Harnesses appeared that run the
loop against your own repository, in a terminal, an editor, a desktop app, or a browser,
all on one engine [@claudecode2026overview]. And a standard emerged for plugging tools in:
the Model Context Protocol, which its own site defines as an open-source standard for
connecting AI applications to external systems [@mcp2026site].

Why this matters for research now, and not two years ago. The June post makes three
observations from practice [@denolle2026three]. Retrieval got good enough that literature
review is close to a solved problem for a working scientist, with models grounding claims
in real papers rather than inventing them. Tool results are facts the model has to read:
when it runs your test and the test fails, the failure is in its window. And the harness
runs against your repository, so the unit of work is a pull request rather than a pasted
snippet. Hold the sceptic's question, "why an agent rather than a script", until segment
20 to 27, where the answer is the spec.

**Timing.** Three minutes if the timeline slide is walked once and not narrated twice.

## 3 to 8 min. What an agent is, mechanically

**Slides**

5. Three columns: open-weight model, private model, and what a prompt does.
6. Chat, script, agent ([](#fig-agent-loop)).
7. The whole thing as code: ten lines, one tool call as JSON, what the harness is.

```{figure} ../../img/agent-loop.svg
:name: fig-agent-loop
:width: 100%

Three ways to put a language model to work. In a chat session (A) the human closes every
loop. In a fixed workflow script (B) every branch was written in advance. In an agent loop
(C) the model reads the result of its last action and decides the next one; the human sets
the goal, the rules, and the stop condition.
```

**Speaker notes**

Three definitions first. A *model* is a function from a token sequence to a probability
distribution over the next token. An *open-weight* model is one whose parameters you can
download and run on your own hardware; HazEvalHub's prototype ran a 7 billion parameter
Qwen and an 8 billion parameter Llama locally next to cloud models
([HazEvalHub](../../chapters/hazevalhub.md)). A *private* model is reached only through a
vendor's API: you never see the weights, you pay per token, and the vendor can change the
model under you. "Writing a prompt" places text in the model's window and asks for a
continuation. Nothing else happens; a chat interface hides that by re-sending the
transcript on every turn.

Then the figure. Panel A is chat: you close every loop, and quality is bounded by your
patience for closing loops. Panel B is the workflow script everyone here already writes:
deterministic, every branch written in advance, and an unexpected input is a crash that a
person reads about in a log. Panel C is the loop. The model is given a goal and tools; it
gathers context, acts, verifies, repeats. The difference from A is that the model closes
the loop. The difference from B is that the model chooses the next step from what it just
observed, so an unexpected state becomes a decision, which can be wrong or endless; a crash
at least stops. The four verbs are our labels for what the tool calls turn out to be. The
model has no stages, only one token stream.

*The whole thing, mechanically.* This is the slide the room needs. The model is called once
per turn with the whole message list and returns tokens. If the returned tokens end in a
structured tool-call block, the program around the model, the *harness*, parses it, checks
permissions, runs the function, appends the result as a new message, and calls the model
again. Nothing else happens: no memory, no execution inside the model, no stages.

```python
messages = [system_prompt, context_file, tool_schemas, task]
while True:
    out = model(messages)                      # one API call: tokens in, tokens out
    if out.stop_reason != "tool_use":
        break                                  # plain text: the model says it is done
    if not permitted(out.tool, out.args):      # the harness pauses here, not the model
        result = "denied by user"
    else:
        result = run(out.tool, out.args)       # shell, file, web, GitHub ...
    messages += [out, tool_result(result)]     # the result re-enters the window
```

A tool call is structured tokens, for example
`{"name": "bash", "input": {"command": "pixi run spellcheck"}}`; the model was
post-trained to emit that format and the harness only parses it. Why a tool at all:
next-token prediction cannot execute, count, or do arithmetic reliably, and a shell with
Python in it is the workaround. A subagent is this same loop started again with a fresh
message list, launched by a tool call, whose final text comes back as a tool result. A
permission prompt is the harness pausing between parse and run; a denial is just a string
the model reads next. Say once which words are one vendor's conventions (`CLAUDE.md`,
skills, `claude -p`) and which are general (the loop, `AGENTS.md`, MCP), because someone
will ask whether this is a Claude course. It is not; the loop is the same everywhere.

The loop is only as good as its *verify* step: an agent that cannot run the tests, or is
not told to, will report success on the strength of having edited a file. And the loop has
no natural end. It stops when the model says it is done, when a budget runs out, or when a
person kills it. We will see all three today.

**Timing.** Five minutes. The code slide deserves two of them.

**Speaker notes**

*The context file.* Every coding agent looks for a standing instruction file in the
repository root. Claude Code reads `CLAUDE.md`, and the vendor documentation says it can
also read an `AGENTS.md` written for other coding agents [@claudecode2026overview]. Ours is
worth showing for what it is not. `CLAUDE.md` is five lines that point at `AGENTS.md`.
`AGENTS.md` fits on one screen: what the repo is, the layout, the build commands, five
conventions, and one paragraph about persona reviews. It does not explain MyST, does not
restate the contributing guide, and does not tell the agent how to write Markdown. The
March post frames this as three layers: a knowledge anchor, standing instructions, and the
situated prompt; the first two determine output quality, and the instructions are a living
document [@denolle2026beforeprompt].

*Tools.* A tool is a function the harness exposes to the model with a name, a description,
and a JSON schema for its arguments. The core set for research work is small: read and
write files, run a shell command, fetch a web page, search the web, call the GitHub API.
Everything the agent does to the world goes through this interface, which is why the
permission model lives here too.

*Skills.* A skill is a folder with a `SKILL.md` and any reference files it needs. The
harness puts every description into the window at startup; the *model* decides to use a
skill, and only then does the harness load the body. So a skill costs its description on
every call, whether or not it fires, and its body only when loaded. That is why the
description is the part to keep short, and why "fix the description" is the remedy when a
skill does not trigger. This repository ships one, `plain-voice`, which strips
language-model vocabulary out of prose; its description is about 60 words, its body about
2300. We build a second one live in segment 27 to 33.

*Subagents.* A subagent is an agent launched by an agent, with a fresh context window, its
own tool set, and one task. Only its final report comes back to the parent. This repository
defines ten of them under `.claude/agents/`: reviewer personas that each read the live site
and file a structured review under `review-logs/`. Three things to notice. Each persona
gets a fresh window and undivided attention; ten reviews do not cost fewer tokens than one,
since each re-sends its own system prompt, context file and tool schemas. Isolation stops
reviewers copying each other but does not remove the weights they share, so convergence
between them is a lead to check, not a statistic. And the output is a dated file, which is
the beginning of an audit trail.

```{figure} ../../img/agents-subagents.svg
:name: fig-agents-subagents
:width: 100%

A subagent is the same loop started again with a fresh message list. Only its final report
re-enters the parent, as a tool result, which is also where injected text would enter.
```

*Anatomy of one agent, and orchestrator versus specialist.* The persona reviewers are the
best in-house example of a specialised agent, because everything that makes one is a file
you can open. The agent definition carries a tools allow-list and points at three files it
reads at run time: the persona's own `SKILL.md` (checks in order, weights, vocabulary
limits, a signature question), the shared `method.md` (what to open, a 30-minute timebox,
read no other review), and the shared `rubric.md` (eight dimensions, a four-level severity
scale, evidence rules, and the exact report format). Ten of these run against the same
rubric and a synthesis step merges them, keeping convergent findings, keeping divergent
ones divergent, and reporting scores as a table rather than an average. The general
pattern: the orchestrator holds a broad goal and only the reports; the specialist holds the
whole input for a bounded time and writes one structured file.

*MCP.* The Model Context Protocol is an open-source standard for connecting AI
applications to external systems, in its own site's words, which offers the analogy of a
USB-C port for AI applications [@mcp2026site]. The agent is the client; each service runs a
server that advertises its tools with the same name-description-schema triple as a native
tool. The practical effect is that adding a capability is a configuration line, not a code
change. The risk is the same as the benefit: every server you connect adds tool descriptions
to the window and adds a party whose output the model will treat as data to act on.

*The context window.* The window is finite. It holds, in order, the system prompt, the
context file, the tool and skill descriptions, and then the running transcript. Tool
results are the part people forget: one `cat` of a large log can consume more of the window
than the whole conversation so far. When the window fills, the harness compacts, and
compaction is itself a model call: the harness asks the model to summarise the older
messages, then swaps them for the summary, so the loss is sampled text, not a deterministic
truncation. A rule stated in the first prompt may not survive; a file read at minute two
may have to be read again. And recall drops for material in the middle of a long context
relative to either end [@liu2024lost]; an agent that "read" forty files sampled them. In
practice: invariant rules go in the context file, not the prompt; big reads go to a
subagent; a new task gets a new session; and when a well-behaved agent starts to drift,
suspect the window before the model.

```{figure} ../../img/agents-context-window.svg

:width: 100%

What is in the window, which part is re-sent every turn, which part is compacted, and what
compaction loses.
```

**Speaker notes**

The vendor documentation lists the surfaces: the terminal, IDE extensions for VS Code and
JetBrains, a desktop app, and the web, all connecting to the same engine so a repository's
context file, settings and MCP servers work across all of them [@claudecode2026overview].
For this room the useful cut is different: what can it touch, and who is watching.

*Browser chat.* The chat tab at the vendor's site. It cannot see your files or run your
code. It is the right tool for questions, drafts and reading papers, and the wrong tool for
anything that ends in a commit. Most people in the room have used only this, and most of
what they believe about "AI coding" comes from pasting snippets into it.

*The app.* The desktop app has a Chat tab and a Code tab. The Code tab is the agent: it runs
against a directory on your machine and shows each diff visually before it lands, and the
documentation notes it can run several sessions side by side and schedule recurring tasks.
The point to make is that Chat and Code are the same model with and without the loop and
the tools; switching tabs is switching from panel A to panel C of the figure.

*The editor.* The VS Code and JetBrains extensions put the same agent inside the editor,
with inline diffs and plan review. This is the mode for changes you want to read line by
line as they happen. TODO: one screenshot from a real session on this repository.

*The CLI.* The terminal is the full-featured surface. Interactive `claude` for exploration
and anything you want to watch; `claude -p` for the non-interactive mode, which takes a
prompt, runs the loop without a terminal, and exits, so it can be piped, scripted, and run
in CI [@claudecode2026overview]. That is the mode the cascadia practice used: a scheduler
pulled open GitHub issues, handed each to a headless run under a standing instruction to
make the smallest change that resolves the issue and open a pull request, and moved to the
next. One issue per run, one run per issue.

## 20 to 27 min. Where it pays off for you

**Slides**

17. The five uses ([](#fig-agents-payoff)).
18. Write the spec first: what a good one contains.
19. Live: a bounded run with a real act and a real verify.
20. Show me the raw data: the check that scales.

```{figure} ../../img/agents-payoff.svg
:name: fig-agents-payoff
:width: 100%

Where an agent pays off in a computational-science workflow. You write the spec and you
look at the raw data; the agent works against the spec in between.
```

**Speaker notes**

This is the answer to "why an agent rather than a script". A script is the right tool when
you already know every step. An agent is the right tool when you can state what done looks
like but not yet how to get there, and when getting there is mostly typing you have done
before. Five uses, from this group's practice, in the order they happen in a project.

*Write the code specification.* Before any code: what the program takes, what it produces,
which conventions it follows, what a passing test looks like, and what is out of scope. Ask
the agent to draft the spec from a conversation and then edit it yourself; the spec is the
contract and everything after is checked against it. The June post's phrase for the
division of labour is that the scarce resource is the human bandwidth to check the work;
the spec is what makes checking possible [@denolle2026three].

*Intent- and goal-oriented coding.* "Implement section 3 of the spec; stop when the first
test in `tests/test_io.py` passes" rather than "write a function that opens the file". You
state the goal and the stop condition; the agent picks the steps. This is the mode the
figure's panel C describes, and it is where the loop earns its cost.

*A repository template.* "Set up a Python repository for X using Y" or "using best
current standards": a `pyproject`, a test directory with one passing test, continuous
integration that runs it, a README that says how to install and run, a licence, a
`.gitignore`. This is an afternoon of boilerplate that the agent does in minutes, and the
coordination plan's `gaia-template-agent` is this use made reusable.

*All the CI tests for X.* "Write the tests for module X, run them, fix what fails, and do
not change X to make a test pass." The tests are the verify step for every later change;
this is the use the vendor documentation itself puts first
[@claudecode2026overview].

*Make sure you can see the raw data.* Ask the agent to plot the raw waveforms, the
intermediate arrays, the first and last rows, at every stage of a pipeline, and to save
those figures where you will look. This is how you check an agent's work without reading
every line it wrote: if the raw data look wrong, the pipeline is wrong, whatever the tests
say. It is the one use on this list that is specific to science, and the one the room
should leave with.

*The live demo.* Before the talk, add a scratch page under `book/teaching/` with one
misspelling; do not commit it, a committed misspelling fails CI. Open the agent in this
repository and say: the spellcheck fails, fix it and show me it passes. The audience
watches `pixi run spellcheck` run, the page get read, one word get edited, the check rerun
and exit 0. Two minutes. The task was chosen because it has a real act and a real verify,
and because the pass condition is the repository's own check rather than the model's
opinion. If the agent edits more than one word, that is the minimal-change rule being
broken in front of the room; say so. Delete the scratch page afterwards.

**Timing.** Seven minutes: one per use, two for the demo.

**Speaker notes**

Three ways, in increasing order of how much you own.

*A skill.* A folder with a `SKILL.md`: a name and a description in the front matter, the
instructions below. Build one live. The problem: the governance page
[How we work](../../governance/how-we-work.md) carries the acknowledgement wording for the
three linked NSF awards and requires it verbatim; an agent asked to "add the
acknowledgement" will paraphrase. The skill: `nsf-acknowledgement`, whose body says to read
the wording from the page at use time, insert it verbatim with all three award numbers, and
append the seed-grant sentence when it applies. Type it, save it, then ask in a fresh
session for "a funding acknowledgement on `mt-rainier.md`" and watch whether it triggers.
If it does not, the description did not match; fix it in front of the room. That failure is
the more instructive outcome. There is a tradeoff to name: a longer description with more
trigger phrases fires more reliably, because the model is the matcher, and costs more per
call. What a skill is not: it is not a tool, it executes nothing new; it is not a subagent,
it runs in the parent's window. It is a procedure written once by someone who knew the
rule.

*An agent definition.* A Markdown file with a name, a description, a tools allow-list and
instructions, which the harness runs as a subagent with a fresh window. The persona
reviewers under `.claude/agents/` are ten of these; copy one and change the persona.
Tutorial 3 does exactly that.

*A loop in Python.* For anything the harness does not do, the vendor SDK exposes the loop
directly. With the Python SDK, a tool is a decorated function and the runner drives the
loop; twelve lines is a working agent with one tool, as documented in the SDK's own
reference, from which the shape below is taken:

```python
import anthropic
from anthropic import beta_tool

client = anthropic.Anthropic()

@beta_tool
def spellcheck(path: str) -> str:
    """Run the repository spellcheck on one file and return its output."""
    ...  # subprocess.run(["codespell", path], ...)

runner = client.beta.messages.tool_runner(
    model="claude-opus-5", max_tokens=16000, tools=[spellcheck],
    messages=[{"role": "user", "content": "Fix the misspelling in docs/demo.md."}],
)
for message in runner:   # one iteration per model turn; stops when no tool is called
    print(message)
```

The same reference documents the manual loop underneath: call `messages.create`, check
`stop_reason`, run each `tool_use` block, append a `tool_result` carrying the block's id,
repeat. That is the code slide from segment 3 to 8 with real names. For a batteries-included
harness as a library, with file tools, subagents and permissions, the vendor documentation
points at its Agent SDK [@claudecode2026overview]; other vendors have equivalents. TODO:
verify the runner example against the installed SDK version before it is shown, and add
the Agent SDK link from a fetched page.

**Timing.** Six minutes: four for the skill, two for the code.

## 39 to 45 min. Guardrails, trajectories, cost, reproducibility

**Speaker notes**

*Guardrails.* Three are in the coordination plan (section 6): a human approves anything
outward-facing, agents draft it; no fabricated DOIs or citations, provenance must be real;
secrets stay in GitHub Secrets and never in a repository. Two more come from practice: the
minimal-change rule, and bounded runs. The June post adds a structural one: agents that
critique other agents, with the critique on the record [@denolle2026three].

*Trajectory capture.* A trajectory is the full sequence of prompts, outputs, tool calls and
results for one run. We need it to audit, to score process and not only outcome, and to
reproduce. Four candidate mechanisms, none verified for our setup: the harness's own session
log; structured JSON output from headless runs; an evaluation harness that wraps the agent,
which is what the FrugalMind prototype does; a logging proxy in front of the model API. The
decision belongs to the group: which default, where stored, who may read.

*Why two runs differ.* Tutorial 4 scores reproducibility as the fraction of identical
outputs across N runs. The next token is sampled, not taken as the argmax, and vendor APIs
expose no seed. Batched inference on shared accelerators is not bit-reproducible even at
temperature zero. A model name can point at new weights, so the version string must be
pinned. And the world moves: the page, the dataset, the repository the agent touched differ
between runs, and only the trajectory records what it saw. Reproducibility of an agent run
is statistical: report N, pin versions, keep every tool result.

*Cost.* One of the three June experiments ran at about 200 dollars a month in API charges
[@denolle2026three]. HazEvalHub's prototype scores every submission on three questions and
plots cost against performance ([HazEvalHub](../../chapters/hazevalhub.md)); its early
result, as the page states it, is that free local 7 to 8 billion parameter models reach
perfect scores on configuration tasks once given domain skills and fail numerical code
generation, where only cloud models succeed, at about 0.56 without skills and 0.76 with.
Task counts and the number of runs behind those figures are not on the page and are a
TODO. Cost is a first-class axis for every agent we ship, recorded per run and reported
next to accuracy.

*Reproducibility.* The June post argues that if an agent cannot reproduce your work, neither
can your collaborators, and proposes a Reproducibility Statement in every paper beside the
data availability statement [@denolle2026three]. The coordination plan already requires a
provenance YAML and an RO-Crate per agent and publication. The missing link is the
trajectory inside the provenance record, which is what
[tutorial 4](tutorials/04-evaluating-agent-runs.md) builds toward.

*The tutorials.* Four stubs under Teaching, code cells to be filled with eScience: anatomy
of an agent, your first skill, subagents and orchestration, evaluating runs. Ask who joins
the dry run.

**Timing.** Six minutes for five topics; trajectory capture is posed as a question, not
answered.
