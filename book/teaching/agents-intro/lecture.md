## 0 to 1 min. Models, prompts, and the word "agent"

**Slides**

1. Title slide. *AI agents for GAIA: what they are, what they are made of, how we run them.*
2. Three columns: *open-weight model*, *private model*, *agent*.

**Speaker notes**

Three words need fixing before anything else.

A *model* is a function from a token sequence to a probability distribution over the next
token. An *open-weight* model is one whose parameters you can download and run on your own
hardware. HazEvalHub's first prototype ran two such models locally, a 7 billion parameter
Qwen and an 8 billion parameter Llama, and scored them next to cloud models
([HazEvalHub](../../chapters/hazevalhub.md)). A *private* model is one you reach only
through a vendor's API. You never see the weights, you pay per token, and the vendor can
change the model under you. Most of what we will talk about today applies to both. The
differences that matter for us are cost, data governance, and reproducibility, and we come
back to those at the end.

"Writing a prompt" means placing text in the model's context window and asking for a
continuation. Nothing else happens. The model does not read a file, run code, or remember
the previous conversation unless that text is placed in front of it again. A chat interface
hides this by re-sending the transcript on every turn.

An *agent* is a model wrapped in a loop that lets it act. The loop gives the model tools,
executes the tool calls the model emits, and feeds the results back into the context. The
model is still only predicting tokens. What changed is that some of those tokens are now
commands, and something runs them.

**Timing.** One minute is not enough for three definitions and a distinction. Expect this
to take two to three minutes, and take them from segment 6 to 14, which has slack.

## 1 to 6 min. Agents versus chatbots: the loop

**Slides**

3. Figure: chat session, fixed script, agent loop side by side ([](#fig-agent-loop)).

```{figure} ../../img/agent-loop.svg
:name: fig-agent-loop
:width: 100%

Three ways to put a language model to work. In a chat session (A) the human closes every
loop. In a fixed workflow script (B) every branch was written in advance. In an agent loop
(C) the model reads the result of its last action and decides the next one; the human sets
the goal, the rules, and the stop condition.
```

**Speaker notes**

The figure has three panels. Walk them left to right.

Panel A is a chat session. You ask, the model answers, you read the answer, you decide what
to ask next. The model never touches anything. Every loop is closed by you, and the quality
of the result is bounded by your patience for closing loops.

Panel B is the workflow script most of us already write: a Snakemake rule, a GitHub Action,
a shell script that downloads, converts and plots. It is deterministic, which is its virtue.
Every branch was written in advance, which is its limit. When the input is not what the
author expected, the script fails, and a person reads the log.

Panel C is the agent loop. The model is given a goal and a set of tools. It *gathers
context*: reads the files, lists the directory, fetches the issue. It *acts*: runs a
command, edits a file, calls an API. It *verifies*: reads the test output, checks the
diff, re-reads the file it just wrote. Then it *repeats* until it judges the goal met or
hits a stop condition. The difference from panel A is that the model closes the loop. The
difference from panel B is that the model chooses the next step from what it just
observed, so an unexpected state becomes a decision, which can be wrong or endless; a crash
at least stops. The four verbs are our labels for what the tool calls turn out to be. The
model has no stages, only one token stream, and the next slide shows the whole thing as
code.

*The whole thing, mechanically.* This is the slide a sceptic needs. The model is called
once per turn with the whole message list and returns tokens. If the returned tokens end in
a structured tool-call block, the program around the model, the *harness*, parses it,
checks permissions, runs the function, appends the result as a new message, and calls the
model again. Nothing else happens: no memory, no execution inside the model, no stages.

```python
messages = [system_prompt, context_file, tool_schemas, task]
while True:
    out = model(messages)                      # one API call: tokens in, tokens out
    if out.stop_reason != "tool_use":
        break                                  # plain text: the model says it is done
    if not permitted(out.tool, out.args):      # the harness pauses here, not the model
        result = "denied by user"
    else:
        result = run(out.tool, out.args)       # shell, file, web, GitHub ...
    messages += [out, tool_result(result)]     # the result re-enters the window
```

A tool call is structured tokens, for example
`{"name": "bash", "input": {"command": "pixi run spellcheck"}}`, and the model was
post-trained to emit that format; the harness only parses it. Why a tool at all:
next-token prediction cannot execute, count, or do arithmetic reliably, and a shell with
Python in it is the workaround. A subagent is this same loop started again with a fresh
message list, launched by a tool call, whose final text comes back as a tool result. A
permission prompt is the harness pausing between parse and run; a denial is just a string
the model reads next. Say once which words are one vendor's conventions (`CLAUDE.md`,
skills, `claude -p`) and which are general (the loop, `AGENTS.md`, MCP), because someone
will ask whether this is a Claude course.

The loop is only as good as its *verify* step: an agent that cannot run the tests, or is
not told to, will report success on the strength of having edited a file. And the loop has
no natural end. It stops when the model says it is done, when a budget runs out, or when a
person kills it. We will see all three today.

The division of labour we have settled on in the group is written up in the June blog post
[@denolle2026three]: scientific direction, judgement of rigour, and the check against
common sense stay human. Literature search, pipeline construction, method implementation,
and the first pass at critique can be handed to agents. The post's phrasing is that the
scarce resource is no longer the ability to do the work but the human bandwidth to check
it. Hold that thought until the guardrails segment.

**Timing.** Five minutes is right if the figure does the work. Do not narrate the four
verbs twice.

**Speaker notes**

*The context file.* Every coding agent looks for a standing instruction file in the
repository root. Claude Code reads `CLAUDE.md`; the cross-vendor convention is
`AGENTS.md`. Ours is worth showing because of what it is not. `CLAUDE.md` is five lines
that point at `AGENTS.md`. `AGENTS.md` fits on one screen: what the repo is, the layout,
the build commands, five conventions, and one paragraph about persona reviews. It does not
explain MyST, does not restate the contributing guide, and does not tell the agent how to
write Markdown. It tells the agent where the table of contents lives and which directory
never to edit. That is the job: the facts an experienced collaborator would need on day
one and would not find by reading the code.

The March blog post [@denolle2026beforeprompt] frames this as three layers: a knowledge
anchor (the documents the agent is grounded in), standing instructions (the rules file),
and the situated prompt (this task, this audience). The post's claim is that the first two
layers, not the prompt, determine output quality, and that the instructions are a living
document rather than a one-time setup. Ours has been rewritten several times since June.

*Tools.* A tool is a function the harness exposes to the model with a name, a description,
and a JSON schema for its arguments. The model emits a call; the harness runs it and
returns the result as text. The core set for research work is small: read and write files,
run a shell command, fetch a web page, search the web, and call the GitHub API. A Python
interpreter is just the shell tool with `python` in front. Everything the agent does to the
world goes through this interface, which is why the permission model lives here too: each
tool call can be allowed, denied, or gated on a prompt to the user.

*Skills.* A skill is a folder with a `SKILL.md` and any reference files it needs. The
front matter carries a name and a one-line description; the body carries the instructions.
The harness puts every description into the window at startup; the *model* decides to
use a skill, and only then does the harness load the body. So a skill costs its
description on every call, whether or not it fires, and its body only when loaded. That is
why the description is the part to keep short, and why "fix the description" is the
remedy when a skill does not trigger. This repository ships one, `plain-voice`, which
strips language-model vocabulary out of prose (`.claude/skills/README.md`); its
description is about 60 words after trimming on this branch, its body about 2300. We
will build a second one live in segment 24 to 33.

*Subagents.* A subagent is an agent launched by an agent, with its own fresh context
window, its own tool set, and a single task. When it finishes, only its final report comes
back to the parent. This repository defines ten of them under `.claude/agents/`: reviewer
personas (a climate-risk CTO, a foundation program officer, a first-year PhD student, and
so on) that each read the live site and file a structured review under `review-logs/`.
Three things to notice. Each persona runs in isolation, so each gets a fresh window and
undivided attention; ten reviews do not cost fewer tokens than one, since each re-sends
its own system prompt, context file and tool schemas. Isolation stops reviewers copying
each other but does not remove the weights they share, so convergence between them is a
lead to check, not a statistic. And the output is a file with a date on it, which is the
beginning of an audit trail.

```{figure} ../../img/agents-subagents.svg
:name: fig-agents-subagents
:width: 100%

A subagent is the same loop started again with a fresh message list. Only its final
report re-enters the parent, as a tool result, which is also where injected text would

```

*Anatomy of one agent, and orchestrator versus specialist.* The persona reviewers are the
best in-house example of a specialised agent, because everything that makes one is a file
you can open. The agent definition carries a tools allow-list and points at three files it
reads at run time: the persona's own `SKILL.md` (checks in order, weights, vocabulary limits,
a signature question), the shared `method.md` (what to open, a 30-minute timebox, read no
other review), and the shared `rubric.md` (eight dimensions, a four-level severity scale,
evidence rules, and the exact report format). The output is one dated file under
`review-logs/`. Ten of these run independently against the same rubric and a synthesis
step merges them, keeping convergent findings, keeping divergent ones divergent, and
reporting scores as a table rather than an average. That split is the general pattern: the
orchestrator holds a broad goal and only the reports; the specialist holds the whole input
for a bounded time and writes one structured file.

*MCP.* The Model Context Protocol is the interface through which an agent discovers and
calls tools that live outside the harness: a web search service, a GitHub server, a
calendar, a database, a Slack workspace. The agent is the client; each service runs a
server that advertises its tools with the same name-description-schema triple as a native
tool. The practical effect is that adding a capability to an agent is a configuration
line, not a code change. The risk is the same as the benefit: every server you connect
adds tool descriptions to the context and adds a party whose output the model will treat
as data it should act on. TODO: link the protocol specification from a fetched page
rather than from memory.

*Keep the standing files short.* The context file, the skill descriptions, and the tool
schemas are loaded into the window before the task begins, on every turn. A long
`AGENTS.md` is paid for on every call, competes with the task's own material for the
model's attention, and buries the three rules that matter under thirty that do not. The
translator project made the same choice for its discipline summaries: about 350 words
each, so that baseline awareness does not dominate the window
([Gaia Translator](../../chapters/gaia-translator.md)). The rule of thumb we use: if a
sentence in the context file would not change what the agent does, delete it.

*The truth about the context window.* The window is finite. It contains, in order, the
system prompt, the context file, the tool and skill descriptions, and then the running
transcript: your prompts, the model's replies, every tool call and every tool result.
Tool results are the part people forget. A single `cat` of a large log or a directory
listing of a data lake can consume more of the window than the entire conversation so far.
When the window fills, the harness compacts: it summarises the older transcript and
continues from the summary. Compaction is itself a model call: the harness asks the model
to summarise the older messages, then swaps them for the summary, so the loss is sampled
text, not a deterministic truncation. A rule you stated in the first prompt may not
survive into the summary; a file the agent read at minute two may have to be read again.
And recall drops for material in the middle of a long context relative to either end
[@liu2024lost]; an agent that "read" forty files sampled them. That citation was
transcribed from the MLGEO lecture 3 references and its DOI is still to be verified.

```{figure} ../../img/agents-context-window.svg
:name: fig-agents-context-window
:width: 100%

What is in the window, which part is re-sent every turn, which part is compacted, and what
compaction loses.
```

In practice: put invariant rules in the context file, not in
the prompt, because the context file is re-read and the prompt is compacted. Use subagents
to isolate reads of large material. Start a new session for a new task rather than
continuing a long one. And when an agent that was behaving well starts to drift, suspect
the window before suspecting the model.

**Timing.** Eight minutes for seven pieces and two diagrams is tight, and the slack has
already been lent to segment 0 to 1. If it runs long, cut slide 13 (MCP) to one sentence and
show only one of slides 14 and 15; tutorial 3 covers both.

**Speaker notes**

We build a skill that solves a real, small problem in this repository. The governance page
[How we work](../../governance/how-we-work.md) carries the acknowledgement wording for the
three linked NSF awards and requires it to be used verbatim wherever it is cited;
`AGENTS.md` repeats that rule. An agent asked to "add the NSF acknowledgement" to a page
will, left to itself, paraphrase. A skill fixes that.

The format, from this repository's own skills README: a folder under `.claude/skills/`
containing a `SKILL.md` with `name` and `description` in the front matter and the
instructions below. The description is what the harness matches against; the body is
what it loads.

Live steps, in order:

1. Create `.claude/skills/nsf-acknowledgement/SKILL.md`.
2. Front matter: name `nsf-acknowledgement`; description along the lines of "Insert the
   agreed GAIA acknowledgement wording for the NSF awards, verbatim, when a page, talk,
   poster, or paper needs an acknowledgement or funding statement."
3. Body: three instructions. Read the wording from
   `book/governance/how-we-work.md` rather than from this file, so there is one source of
   truth. Insert it verbatim, including all three award numbers. If the seed grant or the
   Paros Center contributed, append the second sentence from the same page.
4. Save. Ask the agent, in a fresh session, to "add a funding acknowledgement to
   `book/chapters/mt-rainier.md`". Watch whether the skill triggers without being named.
5. Then invoke it by name and compare.

What to say while typing. The body reads the source page instead of embedding the
wording: that is the difference between a skill and a snippet. A snippet goes stale. The
description is short because it sits in the window on every call, fired or not; a long
one is paid for on every turn of every session. There is a tradeoff to name: a longer
description with more trigger phrases fires more reliably, because the model is the
matcher, and costs more per call. `plain-voice` chose reliability and was trimmed on this
branch from about 150 words to about 60 by moving its provenance into the body. The three
instructions are imperative and specific;
a skill that says "be careful with acknowledgements" would load and do nothing.

What a skill is not. It is not a tool: it cannot execute anything the agent could not
already execute. It is not a subagent: it runs in the parent's context, not a fresh one.
It is a packaged procedure, and its value is that the procedure was written once by
someone who knew the rule.

**Timing.** Nine minutes is generous for a three-instruction skill. Use the surplus to
let the audience propose the second skill they would write, and take two suggestions.
Rehearse step 4; if the skill does not trigger on its own, say why (the description did
not match) and fix the description in front of them. That failure is more instructive
than the success.

**Speaker notes**

*Guardrails.* Three are already in the coordination plan
(`project_coordination/03-ai-tools-and-evals.md`, section 6): a human approves anything
outward-facing, agents draft it; no fabricated DOIs or citations, provenance must be real;
secrets stay in GitHub Secrets and never in a repository. Two more come from practice.
The minimal-change rule from segment 14 to 24: the smallest diff that resolves the issue,
nothing opportunistic. And bounded runs: a turn limit, a cost limit, and a wall-clock
limit on any run nobody is watching. The June post adds a structural one: agents that
critique other agents, with the critique written to the record
[@denolle2026three].

*Trajectory capture.* This is the open question, and it should be presented as one. A
trajectory is the full sequence of prompts, model outputs, tool calls and tool results
for one run. We need it for three reasons: to audit what an agent did, to score agents
on process rather than only on outcome (the "research-workflow" track in HazEvalHub's
task taxonomy already calls this trajectory scoring), and to reproduce a run. The
candidate mechanisms, none of them verified for our setup:

- The harness's own session log. Claude Code writes a transcript of each session to a
  local directory. TODO: verify the location, format and retention for the current
  version, and whether headless runs write one.
- Structured output from headless runs. `claude -p` can emit JSON rather than plain text,
  which would capture the final result and some metadata. TODO: verify what is included
  and whether intermediate tool calls are.
- An evaluation harness that wraps the agent and records everything, which is what the
  FrugalMind prototype does for its scored tasks. TODO: confirm which harness it uses
  and whether it can wrap an interactive Claude Code session or only a headless one.
- A proxy in front of the model API that logs every request and response. Complete, but
  it captures the vendor's wire format rather than the agent's semantics.

The decision to make, and it belongs to the group: which of these we adopt as the
default for GAIA agents, where the trajectories are stored, and who may read them.

*Why two runs differ.* Tutorial 4 scores reproducibility as the fraction of identical
outputs across N runs, so the audience should hear what makes that fraction less than one.
The next token is sampled, not taken as the argmax, and vendor APIs expose no seed. Batched
inference on shared accelerators is not bit-reproducible even at temperature zero. A model
name can point at new weights without notice, so the version string must be pinned and
recorded. And the world moves: the web page, the dataset, the repository the agent touched
differ between runs, and only the trajectory records what it saw. Reproducibility of an
agent run is therefore statistical: report N, pin versions, keep every tool result.

*Cost.* Two facts and one design choice. The fact from practice: one of the three
experiments in the June post ran at about 200 dollars a month in API charges
[@denolle2026three]. The fact from evaluation: HazEvalHub's prototype scores every
submission on three questions, whether it is right, what it cost, and whether it is
reproducible, and plots cost against performance so that a cheap model that reaches the
same score wins ([HazEvalHub](../../chapters/hazevalhub.md)). The design choice that
follows: cost is a first-class axis for every agent we ship, recorded per run and
reported next to accuracy. The early result on that board, as the HazEvalHub page states
it: free local 7 to 8 billion parameter models reach perfect scores on configuration tasks
once given domain skills, and fail numerical code generation, where only cloud models
succeed, at about 0.56 without skills and 0.76 with. Task counts and the number of runs
behind those figures are not on the page and are a TODO. That is the reason to keep
open-weight models in the comparison rather than assume the vendor model. TODO: per-participant and per-run costs
for the tutorials, in the [compute requirements](compute-requirements.md) document.

*Reproducibility.* The June post argues that if an agent cannot reproduce your work,
neither can your collaborators, and proposes a Reproducibility Statement in every paper
alongside the data availability statement [@denolle2026three]. The coordination plan
already requires a provenance YAML and an RO-Crate with every agent and publication
(`project_coordination/03-ai-tools-and-evals.md`, section 1.2). What we do not yet have
is the link between the two: a trajectory in the provenance record. That is the
concrete thing this lecture should leave the team wanting to build, and it is the
subject of [tutorial 4](tutorials/04-evaluating-agent-runs.md).

**Timing.** Five minutes for four topics is one and a quarter each. It works only if
trajectory capture is presented as a question and not answered. Leave no time for
questions here; the tutorials are where the discussion goes.
